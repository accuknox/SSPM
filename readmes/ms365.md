## Prerequisites

- **Python 3.11+** and the `accuknox-sspm` package installed:
  ```bash
  pip install accuknox-sspm
  # or development install from source
  pip install -e .
  ```
- A **Microsoft 365 tenant** with a **Global Administrator** or **Privileged Role Administrator** account to create the app registration and grant admin consent.

## Setting Up Credentials

The scanner authenticates using **app-only (client credentials) flow** — no user login or MFA prompt is required during the scan.

---

### Step 1 – Create an App Registration

1. Sign in to the [Azure Portal](https://portal.azure.com) as a **Global Administrator**.
2. Navigate to **Microsoft Entra ID → App registrations → New registration**.
3. Fill in the form:
   - **Name**: `accuknox-sspm` (or any descriptive name)
   - **Supported account types**: Accounts in this organizational directory only (single tenant)
   - **Redirect URI**: Leave blank
4. Click **Register**.
5. On the app overview page, copy and save:
   - **Application (client) ID** → used as `--client-id`
   - **Directory (tenant) ID** → used as `--tenant-id`

---

### Step 2 – Create a Client Secret

1. In the app registration, go to **Certificates & secrets → Client secrets → New client secret**.
2. Add a description (e.g. `sspm-scanner-secret`) and choose an expiry (24 months recommended).
3. Click **Add**.
4. **Copy the secret Value immediately** — it is shown only once and is used as `--client-secret`.

> Store this secret in a secrets manager (Azure Key Vault, GitHub Actions secrets, etc.). Never commit it to source control.

---

### Step 3 – Add Microsoft Graph API Permissions

1. In the app registration, go to **API permissions → Add a permission → Microsoft Graph → Application permissions**.
2. Search for and add each of the following permissions:

| Permission | Purpose |
|---|---|
| `Organization.Read.All` | Tenant organization info and branding |
| `Domain.Read.All` | Verified domain list |
| `User.Read.All` | User accounts and properties |
| `Group.Read.All` | Microsoft 365 and security groups |
| `Directory.Read.All` | Directory roles and role members |
| `Policy.Read.All` | Conditional Access, auth methods, authorization, timeout, device registration, cross-tenant policies |
| `RoleManagement.Read.Directory` | PIM role assignments and eligibility schedules, role management policies |
| `AuditLog.Read.All` | Sign-in logs (audit log status probe) |
| `Reports.Read.All` | Per-user MFA registration details |
| `InformationProtectionPolicy.Read.All` | Sensitivity labels / DLP policies |
| `DeviceManagementConfiguration.Read.All` | Intune device compliance policies |
| `DeviceManagementServiceConfig.Read.All` | Intune enrollment restrictions |
| `SharePointTenantSettings.Read.All` | SharePoint tenant-level settings |
| `AccessReview.Read.All` | Identity Governance access review definitions |

3. After adding all permissions, click **Add permissions** to confirm.

---

### Step 4 – Grant Admin Consent

All permissions above are **Application** permissions that require admin consent before they can be used.

1. In **API permissions**, click **Grant admin consent for \<Your Tenant\>**.
2. Click **Yes** to confirm.
3. All permissions should now show a green **Granted** checkmark.

> Only a **Global Administrator** or **Privileged Role Administrator** can grant admin consent.

---

### Step 5 – Collect the Required IDs

You need three values to run the scan:

| Value | Where to find it |
|---|---|
| **Tenant ID** | App registration overview → Directory (tenant) ID |
| **Client ID** | App registration overview → Application (client) ID |
| **Client Secret** | Copied in Step 2 (cannot be retrieved again) |
| **Tenant Domain** *(optional)* | Your primary `.onmicrosoft.com` domain or custom domain |

---

### Step 6 – Verify Access

Test that authentication works before running a full scan:

```bash
# Set credentials as environment variables
export SSPM_TENANT_ID=<your-tenant-id>
export SSPM_CLIENT_ID=<your-client-id>
export SSPM_CLIENT_SECRET=<your-client-secret>

# Quick connectivity test (lists a single user)
curl -s -X POST \
  "https://login.microsoftonline.com/${SSPM_TENANT_ID}/oauth2/v2.0/token" \
  -d "grant_type=client_credentials" \
  -d "client_id=${SSPM_CLIENT_ID}" \
  -d "client_secret=${SSPM_CLIENT_SECRET}" \
  -d "scope=https://graph.microsoft.com/.default" \
  | python3 -c "import sys,json; d=json.load(sys.stdin); print('OK –', d.get('token_type','ERROR'))"
```

Expected output: `OK – Bearer`

## PowerShell Bridge (Exchange / Teams / SharePoint)

Exchange Online Management, MicrosoftTeams, and SharePoint Online Management Shell are Remote PowerShell modules with **no Microsoft Graph REST equivalent**. Roughly 69 CIS controls (Exchange audit/mail-flow settings, Defender Safe Links/Safe Attachments/anti-phishing policies, Teams meeting/messaging/federation policies) can only be read through them. The scanner shells out to PowerShell 7 (`pwsh`) to collect this data.

There are two ways to authenticate the bridge:

| Module | Access-token auth (default) | Certificate auth |
|---|---|---|
| Exchange Online | ✅ uses `--client-secret` you already have | ✅ `--ms365-cert-path` |
| Microsoft Teams | ✅ uses `--client-secret` you already have | ✅ `--ms365-cert-path` |
| SharePoint Online | ❌ not supported by `Connect-SPOService` | ✅ `--ms365-cert-path` (required for CIS 7.2.2, 7.2.7, 7.2.9, 7.2.10, 7.2.11, 7.3.1) |

**The bridge runs automatically** on every scan using your existing `--client-secret` — no extra flags needed — as long as `pwsh` and the required modules are installed. Pass `--ms365-no-powershell-bridge` to turn it off entirely and fall back to Graph-only (old) behavior.

### Prerequisites

1. Install PowerShell 7 and the two modules on the machine running the scan:
   ```bash
   # pwsh itself, if not already installed
   sudo snap install powershell --classic   # or your distro's package / winget/brew equivalent

   pwsh -c "Install-Module ExchangeOnlineManagement, MicrosoftTeams -Scope CurrentUser -Force"
   ```
2. Grant the app registration two extra API permissions, in addition to the Microsoft Graph permissions from [Step 3](#step-3--add-microsoft-graph-api-permissions) above:
   - **`Exchange.ManageAsApp`** — API permissions → Add a permission → **APIs my organization uses** tab → search the *full* name `Office 365 Exchange Online` (searching "Exchange" alone returns nothing, a known Azure portal search bug) → Application permissions → expand **Exchange** → check `Exchange.ManageAsApp`.
   - **`Organization.Read.All`** (Microsoft Graph) — already in the permissions list above; Teams token auth reuses it.
   - Click **Grant admin consent** after adding.

   If `Office 365 Exchange Online` doesn't show up in the portal at all (can happen on fresh/dev tenants), grant it via Microsoft Graph PowerShell instead:
   ```powershell
   Connect-MgGraph -Scopes "Application.ReadWrite.All","AppRoleAssignment.ReadWrite.All"
   $resourceSp = Get-MgServicePrincipal -Filter "appId eq '00000002-0000-0ff1-ce00-000000000000'"  # Office 365 Exchange Online
   $yourSp     = Get-MgServicePrincipal -Filter "appId eq '<your-client-id>'"
   New-MgServicePrincipalAppRoleAssignment -ServicePrincipalId $yourSp.Id `
     -PrincipalId $yourSp.Id -ResourceId $resourceSp.Id `
     -AppRoleId "dc50a0fb-09a3-484d-be87-e023b12c6440"   # Exchange.ManageAsApp, same GUID in every tenant
   ```
3. Assign two Entra directory roles to the app's service principal (**Identity → Roles and administrators** → search the role → *Add assignments* → search your app's name instead of a user):
   - **Exchange Administrator**
   - **Teams Administrator**

With that in place, a plain scan (just `--tenant-id`/`--client-id`/`--client-secret`/`--tenant-domain`) resolves the Exchange and Teams controls automatically. If a permission or role is missing, the affected controls come back `SKIPPED` with the underlying error message rather than failing the whole scan.

### Certificate auth (required for SharePoint; alternative for Exchange/Teams)

1. Generate a self-signed certificate and upload the public half to the app registration:
   ```bash
   openssl req -x509 -newkey rsa:2048 -keyout key.pem -out cert.pem -days 365 -nodes -subj "/CN=sspm-ms365-bridge"
   openssl pkcs12 -export -out sspm-cert.pfx -inkey key.pem -in cert.pem -passout pass:<your-cert-password>
   openssl x509 -in cert.pem -outform der -out cert.cer   # upload this .cer under Certificates & secrets → Certificates
   ```
2. Run with `--ms365-cert-path ./sspm-cert.pfx --ms365-cert-password '<your-cert-password>'`. When a cert path is supplied it takes priority over token auth for Exchange/Teams.
3. Install the SharePoint module as well — `pwsh -c "Install-Module Microsoft.Online.SharePoint.PowerShell -Scope CurrentUser -Force"` — and assign the app's service principal the **SharePoint Administrator** directory role.

   `Connect-SPOService` only supports certificate auth, so six controls stay `SKIPPED` without one: CIS 7.2.2 (`EnableAzureADB2BIntegration`), 7.2.7 (`DefaultSharingLinkType`), 7.2.9 (`ExternalUserExpirationRequired`/`ExternalUserExpireInDays`), 7.2.10 (`EmailAttestationRequired`/`EmailAttestationReAuthDays`), 7.2.11 (`DefaultLinkPermission`), and 7.3.1 (`DisallowInfectedFileDownload`). Microsoft Graph's `/admin/sharepoint/settings` does not expose any of those properties.

## Microsoft Fabric (CIS section 9.1)

The twelve section 9.1 controls read the Fabric admin REST API (`GET https://api.fabric.microsoft.com/v1/admin/tenantsettings`), which is a separate resource from Microsoft Graph — the scanner acquires its own app-only token automatically, no extra flags.

Fabric only accepts a service principal once a Fabric administrator opts in. Until then the API answers `403` and all twelve controls come back `SKIPPED` with that reason. To enable it: **Fabric admin portal → Tenant settings → Developer settings → "Service principals can access read-only admin APIs"** → enable and add this app registration to the allowed security group.

> **Note on the benchmark:** CIS v6.0.1's *Appendix: Summary Table* marks section 9.1 "(Manual)", but each control's own heading and audit procedure says "(Automated)" and cites the REST API. The scanner follows the body, which is why the benchmark has 11 manual controls here rather than 23.

## CLI Reference

```
sspm scan ms365 [OPTIONS]
```

| Option | Env Variable | Required | Description |
|--------|-------------|----------|-------------|
| `--tenant-id TEXT` | `SSPM_TENANT_ID` | Yes | Entra ID tenant GUID |
| `--client-id TEXT` | `SSPM_CLIENT_ID` | Yes | App registration client ID |
| `--client-secret TEXT` | `SSPM_CLIENT_SECRET` | Yes | App registration client secret |
| `--tenant-domain TEXT` | `SSPM_TENANT_DOMAIN` | No | Human-readable domain label (e.g. `contoso.onmicrosoft.com`) used in report titles |
| `--profile TEXT` | — | No | Limit scan to a CIS profile: `"E3 Level 1"`, `"E3 Level 2"`, `"E5 Level 1"`, or `"E5 Level 2"` |
| `--rule TEXT` | — | No | Limit scan to one or more specific rule IDs (repeatable) |
| `--output TEXT / -o` | — | No | Output file stem (default: `sspm-ms365-report`). Generates `<stem>.html` and `<stem>.sarif.json` |
| `--no-html` | — | No | Skip HTML report generation |
| `--no-sarif` | — | No | Skip SARIF report generation |
| `--verbose / -v` | — | No | Print individual findings to the terminal during the scan |
| `--ms365-cert-path TEXT` | `SSPM_MS365_CERT_PATH` | No | Path to a `.pfx` certificate for the PowerShell bridge. Only required for SharePoint — Exchange/Teams use `--client-secret` (token auth) when omitted |
| `--ms365-cert-password TEXT` | `SSPM_MS365_CERT_PASSWORD` | No | Certificate password (passed to the child `pwsh` process via env only, never argv/logs) |
| `--ms365-pwsh-app-id TEXT` | `SSPM_MS365_PWSH_APP_ID` | No | App registration client ID for the bridge (defaults to `--client-id`) |
| `--ms365-sharepoint-admin-url TEXT` | `SSPM_MS365_SHAREPOINT_ADMIN_URL` | No | SharePoint admin center URL (defaults to `https://<tenant-domain-prefix>-admin.sharepoint.com`) |
| `--ms365-no-powershell-bridge` | `SSPM_MS365_NO_POWERSHELL_BRIDGE` | No | Disable the PowerShell bridge entirely, reverting to Graph-only (old) behavior |
| `--ms365-no-exchange-bridge` | `SSPM_MS365_NO_EXCHANGE_BRIDGE` | No | Disable only the Exchange Online PowerShell bridge |
| `--ms365-no-teams-bridge` | `SSPM_MS365_NO_TEAMS_BRIDGE` | No | Disable only the Microsoft Teams PowerShell bridge |
| `--ms365-no-sharepoint-bridge` | `SSPM_MS365_NO_SHAREPOINT_BRIDGE` | No | Disable only the SharePoint Online PowerShell bridge |
| `--ms365-pwsh-path TEXT` | `SSPM_MS365_PWSH_PATH` | No | Path to the PowerShell 7 executable (default: `pwsh`) |
| `--ms365-pwsh-timeout INTEGER` | `SSPM_MS365_PWSH_TIMEOUT` | No | Timeout in seconds for each PowerShell bridge script (default: `180`) |

## Usage Examples

### Basic scan with explicit credentials

```bash
sspm scan ms365 \
  --tenant-id     xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx \
  --client-id     yyyyyyyy-yyyy-yyyy-yyyy-yyyyyyyyyyyy \
  --client-secret "your-client-secret-here" \
  --tenant-domain contoso.onmicrosoft.com \
  --output contoso-cis-report
```

> This alone also resolves Exchange/Teams controls via the PowerShell bridge (token auth, using this same `--client-secret`) — see [PowerShell Bridge](#powershell-bridge-exchange--teams--sharepoint) for the one-time prerequisites. Add `--ms365-no-powershell-bridge` to skip it and get the old Graph-only behavior.

### Scan with the certificate-based bridge (required for SharePoint)

```bash
sspm scan ms365 \
  --tenant-id     xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx \
  --client-id     yyyyyyyy-yyyy-yyyy-yyyy-yyyyyyyyyyyy \
  --client-secret "your-client-secret-here" \
  --tenant-domain contoso.onmicrosoft.com \
  --ms365-cert-path ./sspm-cert.pfx \
  --ms365-cert-password "your-cert-password"
```

### Scan using environment variables (CI/CD)

```bash
export SSPM_TENANT_ID=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
export SSPM_CLIENT_ID=yyyyyyyy-yyyy-yyyy-yyyy-yyyyyyyyyyyy
export SSPM_CLIENT_SECRET=your-client-secret-here
export SSPM_TENANT_DOMAIN=contoso.onmicrosoft.com

sspm scan ms365 --output contoso-report --verbose
```

### E3 Level 1 controls only

```bash
sspm scan ms365 \
  --tenant-id     $SSPM_TENANT_ID \
  --client-id     $SSPM_CLIENT_ID \
  --client-secret $SSPM_CLIENT_SECRET \
  --profile "E3 Level 1" \
  --output e3-l1-report
```

### Run a single rule

```bash
sspm scan ms365 \
  --tenant-id $SSPM_TENANT_ID \
  --client-id $SSPM_CLIENT_ID \
  --client-secret $SSPM_CLIENT_SECRET \
  --rule ms365-cis-5.1.2.1
```

### SARIF output only

```bash
sspm scan ms365 \
  --tenant-id     $SSPM_TENANT_ID \
  --client-id     $SSPM_CLIENT_ID \
  --client-secret $SSPM_CLIENT_SECRET \
  --no-html \
  --output ms365-sarif-only
```

### List all MS365 rules (without scanning)

```bash
sspm rules list --provider ms365
```

## Output Files

Running `sspm scan ms365` produces two files by default:

| File | Format | Description |
|------|--------|-------------|
| `sspm-ms365-report.html` | HTML | Interactive report with summary dashboard, per-rule findings, remediation steps, and evidence |
| `sspm-ms365-report.sarif.json` | SARIF 2.1.0 | Machine-readable findings compatible with GitHub Advanced Security, VS Code SARIF Viewer, and any SARIF-aware toolchain |

### Finding statuses in the report

| Status | Meaning |
|--------|---------|
| `PASS` | Control is compliant |
| `FAIL` | Control is non-compliant; remediation required |
| `MANUAL` | CIS itself classifies the control "(Manual)" — human review required. Exactly 11 of the 140 recommendations, and never more |
| `SKIPPED` | Prerequisites not met, so the control was not evaluated — the finding message says which credential, permission, or licence is missing |
| `ERROR` | Unexpected error during rule evaluation |

## Security Recommendations

- **Use a dedicated app registration.** Do not reuse an existing application — create one specifically for scanning so it can be disabled or deleted independently.

- **Apply least-privilege permissions.** The permissions listed above are the minimum required. Do not add `Write`, `ReadWrite`, or `FullControl` permissions.

- **Rotate the client secret.** Set a calendar reminder before the secret expires. Generating a new secret does not invalidate the old one — you can rotate with zero downtime by creating a second secret, updating the scan config, then deleting the old secret.

- **Store the secret securely.**
  - Local use: environment variable or a `.env` file with `chmod 600`, never in source control.
  - CI/CD: use your platform's secrets manager (GitHub Actions secrets, Azure Key Vault, HashiCorp Vault).

- **Monitor app activity.** The app registration appears in Microsoft Entra sign-in logs. Review it periodically for unexpected authentication events.

- **Restrict by IP (optional).** You can add a Conditional Access policy that restricts the app to specific IP ranges, though this requires an Entra ID P1 or P2 license.
